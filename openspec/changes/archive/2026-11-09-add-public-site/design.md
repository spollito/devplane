# Design: Add the public site

## Context

See proposal.md for why, and the specs for the behavior. What exists today:

- `docs/mockups/landing.html` and `landing.css` are the approved splash page. Their
  content is out of date: "Phase 1 of 4 is in progress", "soon one click in its web UI",
  the Interface layer drawn as in progress, and fonts from Google. `docs/mockups/figure.py`
  rewrites the drawing between its markers.
- The repository is public, and Pages isn't enabled. GitHub Pages serves static files
  only, under `/devplane/`.
- `devplane.css` loads fonts from absolute paths (`/fonts/…`), which would point outside
  `/devplane/` on Pages.
- `ProjectArchiver` is package-private in `templates`, and `archive(template, project)`
  returns a zip's bytes. `GeneratedProjectBuildTests` already constructs
  `ProjectGenerator` directly.
- `CatalogConstraints` holds the identifier pattern, description limit, and messages.
  Several are package-private, and the lifecycle pattern is in `Lifecycle`.
- `./gradlew build` and `build.yml` need no Node. `openspec.yml` already installs Node 22
  in CI, and Playwright MCP and the OpenSpec CLI need it locally.
- `harden-web-ui` changes `devplane.css`'s identifier, table, and breakpoint rules. This
  change builds on them.

## Goals / Non-Goals

**Goals:**

- Nobody can mistake the demo for the real product, or lose anything by using it.
- One source for what's shared. The site uses the app's stylesheet and fonts, not copies.
- Differences between the site and the app that matter fail a check, rather than rely on
  someone remembering.
- `./gradlew build` keeps working with no Node.

**Non-Goals:**

- Sharing templates between Thymeleaf and the demo. The demo's markup is a small, separate
  rendering of the same classes.
- Making the demo complete. It shows the path. Editing services and paging stay out.

## Decisions

### 1. A plain `site/` folder, published by a workflow

```
site/
  index.html        the splash page
  site.css          from docs/mockups/landing.css
  figure.py         draws index.html's figure, as in docs/mockups (not published)
  demo/
    index.html      the shell, with a noscript message
    demo.css        the demo notice, on top of the app's stylesheet
    catalog.js      the demo's rules and data, with no DOM access
    app.js          rendering and routing
    catalog.test.js Node's built-in test runner (not published)
```

Alternatives:

- **Jekyll or another site generator** was rejected: a toolchain for one page and one
  small app.
- **Publishing from `/docs` or a `gh-pages` branch** was rejected. `/docs` would publish
  the architecture notes and mockups, and a branch would hold build output in Git. An
  Actions artifact holds neither.

### 2. `siteBuild` assembles the site from one source

A Gradle `Sync` task, `siteBuild`, writes `build/site/` from:

- `site/`, excluding `figure.py` and `*.test.js`
- `src/main/resources/static/css/devplane.css` into `css/`
- `src/main/resources/static/fonts/` into `fonts/`
- `src/main/resources/static/favicon.svg`
- the generated zip into `downloads/`

The stylesheet and fonts are therefore never copied into Git, and the demo inherits the
app's look automatically. To make that work under `/devplane/`:

- `devplane.css`'s font URLs become relative (`../fonts/…`). The file is served from
  `/css/` in the app and `/devplane/css/` on Pages, so that resolves in both.
- Every link and asset in `site/` is relative.

`StaticAssetsTests` keeps checking that the app's fonts load.

### 3. The zip is generated by the real archiver

`siteDownload`, a Gradle `JavaExec` task, runs a small class in the test source set, in
the `templates` package so it can reach `ProjectArchiver`. It archives `java-rest-api` for
`orders-api`, owned by `payments-team`, with the description `Order management REST API`,
and writes `build/site-download/orders-api.zip`. `siteBuild` depends on it.

- **The test source set**, because production code shouldn't carry a build tool, and
  `ProjectArchiver` needn't become public.
- **It needs no Spring context or database:** the archiver takes a `ProjectGenerator`,
  which is constructed directly, as `GeneratedProjectBuildTests` does.
- **It fails the task** if generation fails, so no site is published.

Alternatives:

- **Committing a zip** was rejected. It would go stale when the template changes, without
  anyone noticing.
- **Starting the app in CI and calling the API** was rejected. It needs PostgreSQL and
  health polling, to reach the same `ProjectArchiver`.
- **Generating a project for any name in the browser** was rejected. It would reimplement
  the generator in JavaScript, and it could differ from the real one. The demo is honest
  that the download is always the example.

### 4. The demo is plain JavaScript, with its logic apart from the DOM

- **`catalog.js`** is an ES module with no DOM access. It holds the sample data, the
  validation rules and messages, list, filter, register, unregister, the simulated
  repository, reset, and relative times.
- **`app.js`** renders each screen with the app's CSS classes, and uses the same text as
  the Thymeleaf pages. It builds elements with a small helper that only uses
  `textContent` and `setAttribute`, and never `innerHTML` with data, so entered text can't
  become markup.
- **Routing** uses the hash (`#/services`, `#/services/orders-api`, `#/register`,
  `#/services/orders-api/unregister`), because Pages has no server to send other paths to
  the app. The URLs can be reloaded and shared.
- **Storage:** `localStorage` under one key, with every read and write in `try`/`catch`.
  If storage is blocked, the demo keeps its data in memory for the visit.
- **Simulated repository:** a timer of about a second, then the result. The state is
  recorded as `simulated`, so the page renders "Simulated. Nothing was created on GitHub."
  and what the real app does, with no URL. Sample services have sample repositories shown
  as plain text.
- **Times:** sample services store an age, not a date, so "2 days ago" stays true.

Alternatives:

- **React or another framework** was rejected: a build step and dependencies for a few
  screens, and the rest of the project doesn't use one.
- **htmx**, as in the app, was rejected. It needs a server to answer with HTML.
- **A service worker pretending to be the server** was rejected: clever, hard to debug, and
  it would still need templates in JavaScript.

### 5. Checks that stop drift

The project's Java tests already run on every build, so the drift checks live there, with
jsoup, which the project already has:

- **`SiteRoadmapTests`:** parses `- [x]` and `- [ ]` lines under the README's phase
  headings (normalizing `*Stretch:*`), and the splash page's roadmap with jsoup. It fails
  on any difference in order, wording, or built state, and names the item.
- **`SiteRulesTests`:** in the `catalog` test package, so it can read the package-private
  constants. It checks that `site/demo/catalog.js` contains the exact identifier pattern,
  lifecycle stages, description limit, and each message.
- **`SiteFieldMessagesTests`:** in the `web` test package, for the "Enter …" messages, which
  `FieldMessages` holds.

`catalog.js` holds these as plain constants so that the check can find them.

Alternative: generating the roadmap or the rules at build time was rejected. It needs a
templating step in `siteBuild`, while a failing test is simple, and tells the author what
to change.

### 6. The workflow

`.github/workflows/pages.yml` runs on pushes to `main` and on pull requests:

- **`build` job:**
  - checks out, and sets up Java 21 and Node 22, as the other workflows do
  - runs `node --test "site/demo/*.test.js"`, then `./gradlew siteBuild`
  - uploads `build/site` with `actions/upload-pages-artifact`
- **`deploy` job:** only on `main`, needs `build`, and runs `actions/deploy-pages` in the
  `github-pages` environment. It has `pages: write` and `id-token: write`. A failed build
  means this job never runs, so the published site stays as it was.

Action versions match what the other workflows use at the time, currently
`upload-pages-artifact@v5` and `deploy-pages@v5`. Workflow permissions stay at
`contents: read` by default.

**Enabling Pages** is a one-time repository setting, with GitHub Actions as the source:
`gh api -X POST repos/spollito/devplane/pages -f build_type=workflow`. It needs admin
access, which only the owner has, so a task asks first.

### 7. Content changes from the mockup

- **Status:** "Phase 1 is complete. Phase 2, deployment, is next."
- **Figure:** `figure.py` redraws Interface as built. Fonts and styles come from `css/` and
  `fonts/`, not Google.
- **Hero actions:** "Try the demo" is primary, and "View the source on GitHub" secondary.
- **"What it does today":** "soon one click in its web UI" becomes "in its web UI, or
  through its REST API".
- **Roadmap:** the README's exact wording, which the mockup had shortened, so the check can
  compare it.
- **Top bar:** gains "Demo".
- **Sizes:** at the mockup's breakpoint, the drawing's labels fell below the guidelines' 12px
  minimum. The hero now stacks below 1100px, and the stacked drawing is at most 760px wide.
  The path diagram stacks at the app's 960px, so its arrows match its layout.
- The mockups stay in `docs/mockups/` as the record of what was approved. Their README says
  `site/` is now the real site.

### 8. The README roadmap and the first publish

The change adds "Public site: a splash page and a try-it demo on GitHub Pages" to Phase 1,
and ticks it in the same pull request, as earlier items were. The site's first publish
happens when that pull request merges, so the task that confirms the live site can only be
ticked afterward, in the archive pull request. PR #9 set the precedent for this with its
real-GitHub check.

### Additions to the UI guidelines

The Public site section changes from "one static page" to a splash page and a demo:

- **Demo notice:** a new component. A `--surface` strip with a `--line` border, above the
  page's content on every demo screen, with its text and two links.
- **Reading scale** applies to the splash page. The demo uses the app's scale, because it's
  showing the app.
- **Only true things:** sample data appears only in the demo, under the notice. Simulated
  results say they're simulated, and sample repositories are never links.
- **JavaScript:** the demo is the only page that needs it, and it says so without it.
- **Screenshot check:** covers the site, at the same widths and with the same long names.

The screenshot check also found that the catalog's Repository column, from `harden-web-ui`,
was too narrow: `octo-dev/auth-service` wrapped, and the row doubled in height. The columns
are rebalanced in `devplane.css` and the guidelines, to Name 22%, Owner 14%, Lifecycle 128px,
Repository 22%, and Updated 112px. That change reaches the real app too.

### Later roadmap items this must not block

- **Phase 2 onward:** new roadmap items fail `SiteRoadmapTests` until the site lists them,
  which is the intended reminder. A finished layer means re-running `figure.py`.
- **A hosted demo, if ever wanted:** the splash page's "Try the demo" link can point
  anywhere. Nothing here assumes the demo stays static.

## Risks / Trade-offs

- [The demo's markup can drift from the real templates] → The stylesheet is shared, so the
  look stays in step. The screenshot check compares the demo against the app's pages.
  Structural drift is accepted for a small demo.
- [A visitor could take the demo for the real product] → The notice is on every screen,
  simulated results say so, and nothing links to repositories that don't exist.
- [The demo's code has no browser tests] → `catalog.js` is unit tested with Node, and
  `app.js` is covered by the browser check. Keeping `app.js` thin limits what that misses.
- [A README roadmap edit now also needs a site edit] → Intended, and the failure message
  says which item.
- [`node --test` adds a tool to CI for this workflow] → It's already used in CI by
  `openspec.yml`, with no packages to install. `./gradlew build` still doesn't need it.
- [The footer publishes the owner's name] → It comes from the approved mockup and the
  public LICENSE file.
- [GitHub Pages' free limits] → A few hundred KB of static files is far below them.

## Migration Plan

Nothing to migrate. To roll back, disable Pages or revert the change. The app doesn't
depend on the site.
